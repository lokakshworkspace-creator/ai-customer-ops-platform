## 1. Modular monolith, not microservices

**Context.** The domain (orders, refunds, tickets) is small and tightly related: a refund needs the order and its payment in one transaction. One developer, one deployable.

**Decision.** One FastAPI process. Each domain area is a module with a service layer (rules, authorisation scoping) and a repository layer (SQL). Today that is `app/modules/orders`, `users`, `refunds` and `tickets` (plus `audit.py`); the tool handlers in `app/tools/handlers/` call those services. Routers stay thin. Phase 2 added two more processes (the outbox relay and the notification consumer) that share the same code and database but run separately; that is the only place the monolith is split.

**Trade-off.** Module boundaries are a convention, not something the runtime or CI enforces (no import-linting yet), and everything scales and deploys together. In exchange there are no network hops, no distributed transactions, and a refund plus its outbox event can commit atomically in one database. Modules can be extracted later because they only talk through their service functions.

## 2. Postgres is the source of truth; Redis is disposable

**Context.** An LLM workflow can be long-running and can be interrupted by a crash, a deploy, or waiting for a human approval.

**Decision.** All durable state, including workflow state, lives in Postgres: `workflow_runs` holds the current FSM `state` and a JSONB `context` checkpoint. Redis is limited to things that can be lost without changing an outcome: cache, rate limiting, and an idempotency *fast path*.

**Trade-off.** Every workflow step costs a database write, and Redis can never be relied on for correctness (the refund `UNIQUE` constraint, not Redis, decides duplicates). The win is that flushing Redis loses speed, not data, and a crashed workflow resumes from its last checkpoint.

**Status.** The `workflow_runs` table exists; no code uses it yet (Phase 3). Redis is provisioned and is currently only pinged by `/health`. Refund idempotency deliberately does **not** use a Redis fast path in Phase 2: the database constraint alone decides, so there is nothing to keep in sync.

## 3. Enums as VARCHAR + CHECK, not native Postgres enums

**Context.** Statuses (`order_status`, `refund_status`, …) and roles are closed sets that will grow as phases add behaviour.

**Decision.** Store each as `VARCHAR(32)` with a named `CHECK` constraint (`ck_<table>_<enum>`, e.g. `ck_refunds_refund_status`), mapped to a Python `StrEnum` via SQLAlchemy `Enum(native_enum=False, create_constraint=True)`.

**Trade-off.** The database column is just a string, so there is no separate type to introspect, and changing the allowed values means dropping and re-adding the constraint (done in one transactional migration). Native enums need `ALTER TYPE … ADD VALUE`, cannot remove values, and are awkward to evolve with Alembic. Plain VARCHAR keeps migrations and raw SQL simple.

**Gotcha — Alembic autogenerate duplicates the CHECK.** For every such column, autogenerate emitted the constraint twice (once from the `Enum` type, once as an explicit `CheckConstraint`), both resolving to the same name, which would fail when applied. Migration `0001` was hand-edited so each enum column is a plain `String(32)` with exactly one named `CHECK`. The rule is recorded in `CLAUDE.md`: *always hand-review new migrations so each enum has exactly one named CHECK.*

**Residual risk.** As far as Alembic's documentation states, autogenerate does not compare CHECK constraints, so `alembic check` will not catch a model/DB mismatch in the allowed values (not re-tested here). The constraints are exercised through the real migration in the test suite (for example, a test inserts an unknown `status` and expects the insert to be rejected), but only for some columns. The status vocabularies for refunds and approvals are a first draft and are on the Phase 2 review list.

## 4. Money is `Numeric(12,2)` plus a currency column

**Context.** Floating-point money produces rounding errors; refunds and policy thresholds compare amounts exactly.

**Decision.** Every money column (`total_amount`, `unit_price`, `amount`) is `NUMERIC(12,2)`, mapped to Python `Decimal`. Orders, payments and refunds carry a `currency` column; `order_items` are priced in their order's currency. The API returns amounts as exact decimal strings (`"1499.00"`), never JSON floats. `CHECK` constraints keep totals non-negative and payment/refund amounts positive.

**Trade-off.** Two fixed decimal places suit rupees, dollars and euros but not currencies with 0 or 3 minor units, and the cap is just under 10^10. Integer minor units (paise) would avoid the scale question but are less readable in SQL and in API payloads; that was judged not worth it here.

## 5. UUID primary keys generated by the application

**Context.** Later phases need to know an entity's id before it is persisted, for example to put it in an outbox event, an idempotent request, or a log line. Sequential integer ids in URLs also invite enumeration.

**Decision.** Every primary key is a `UUID` generated in Python (`default=uuid.uuid4`), not by a database default or sequence.

**Trade-off.** Random UUIDv4 keys are larger than bigints (16 bytes vs 8) and have no insertion locality, which fragments B-tree indexes at scale; they also carry no ordering, so lists order by `placed_at` with `id` only as a tie-break. UUIDv7 would restore time-ordering and could be adopted later without changing the column type. UUIDs are not a security control: authorisation still checks ownership (see decision 6).

## 6. 404, not 403, for other users' resources

**Context.** If `GET /orders/{id}` answered `403` for someone else's order and `404` for a nonexistent one, any customer could probe which order ids exist.

**Decision.** The owner filter is applied inside the repository query (`WHERE id = :id AND user_id = :owner`), so another customer's order is simply "not found": the same status and body as a random UUID. List endpoints and their `total` counts are scoped the same way. Only an explicit `admin` role is unscoped (an allow-list, so any future role defaults to seeing only its own data).

**Trade-off.** A legitimate user who mistypes an id and a user probing someone else's id get the same message, which is slightly less informative for debugging; the request id in the logs recovers that for operators. The test suite compares the two responses directly. Separately, deliberately removing the owner filter (and other variants, run by hand rather than as part of the suite) made those tests fail, which is how their sensitivity was checked.

## 7. The role comes from the database, not the JWT

**Context.** A role claim in a signed token is convenient but stale: a demoted or deactivated user keeps their old powers until the token expires, and a signing-key mistake would mean forged admin tokens.

**Decision.** Tokens carry identity only (`sub`, `iat`, `exp`). `get_current_user` reloads the user from Postgres on every request, rejects missing or inactive users with `401`, and takes the role from that row. `require_role(...)` checks that role and answers `403`. HS256 is pinned and `exp` and `sub` are required.

**Trade-off.** One extra primary-key lookup per authenticated request, and the API is not purely stateless. In return, deactivation, deletion and demotion take effect immediately, and a validly signed token that *claims* `role: admin` gains nothing (covered by tests). There is still no way to revoke an individual token before it expires (listed under known limitations in the README).

## 8. Tests run against real Postgres, schema built by Alembic

**Context.** The behaviours that matter most here are database-level: unique and `CHECK` constraints, `NUMERIC` precision, foreign-key `RESTRICT`, and owner-scoped queries. SQLite would not reproduce them (or the `vector` extension and JSONB).

**Decision.** The test session creates a separate `ops_test` database, rebuilds its schema by running `alembic upgrade head`, and runs each test inside an outer transaction that is rolled back afterwards (commits inside a test only release a SAVEPOINT). The fixtures refuse to run unless the database name ends in `_test`, and a test runs `alembic check` to detect drift between models and migrations. Alembic runs in a worker thread because its async `env.py` calls `asyncio.run()`.

**Phase 2 additions.** Concurrency tests cannot run inside one rolled-back transaction, so a second fixture, `committed_db`, gives each test a pool of separate connections whose sessions really commit; it empties the tables before and after with a guarded `TRUNCATE` (test database only: the name must end in `_test`, and `alembic_version` is skipped). Tests that need the real Redpanda carry the `kafka` marker (see decision 20).

**Trade-off.** The tests need the Docker Postgres running (and Redpanda for the `kafka` subset), the suite is slower than an in-memory database (130 tests in roughly 10–15 seconds at the end of Phase 1; **643 tests** now, 615 of which need Postgres only and take about 2 minutes, 28 more need Redpanda), and tests share one database so they can't run in parallel without more work. The upside is that the migrations themselves are under test and constraint, locking and concurrency behaviour is real.

## 9. Events go through a transactional outbox

**Context.** Phases 2 and 5 need to emit events (refund processed, approval decided) to Redpanda. Publishing directly from a request handler can lose an event if the broker is down after the commit, or emit one for a transaction that later rolls back.

**Decision.** Handlers call `add_event`, which only adds an `outbox_events` row to the caller's session: it never flushes, commits or talks to a broker, so the event commits (or rolls back) with the state change. A separate relay process publishes unpublished rows to Redpanda and marks them published only after the broker acknowledges. Nothing else may produce to Kafka; a test scans the source and fails if a module other than the event modules imports a Kafka client, builds an `OutboxEvent` by hand, or calls `add_event` from an unexpected place.

**Trade-off.** Delivery is at-least-once, so consumers must be idempotent (decision 19), and there is a small publishing delay plus one more process to run. The state change and its event can never disagree.

**Status.** **In place (Phase 2).** Writer, relay, consumer, event schema and failure handling: decisions 17–19 and [`events.md`](events.md).

## 10. INR is the currency

**Context.** The business rules are expressed in rupees: in `rules.yaml` refunds up to ₹500.00 are auto-approved (for the auto-approvable reasons) and larger ones need approval.

**Decision.** `currency` defaults to `"INR"` in the models (a Python-side default, so no migration was needed) and the seed data uses rupee prices (₹299–₹4,999). The column stays `NOT NULL` with no database default, so every insert must state a currency explicitly or through the ORM default.

**Trade-off.** Policy thresholds currently assume a single currency. The `currency` column keeps multi-currency possible, but supporting it would mean per-currency thresholds and a defined conversion story. Rows inserted outside the ORM must set `currency` themselves.

## 11. The policy engine is pure functions over a validated `rules.yaml`

**Context.** Whether a refund may go ahead is the most security-relevant decision in the system, and it must stay explainable and testable even once an LLM is proposing the actions.

**Decision.** `app/policy/engine.py` contains only pure functions: they take frozen inputs (the rules, the `Actor`, a facts object, and the current time as a value) and return a `PolicyResult` (`ALLOW`, `REQUIRE_APPROVAL` or `DENY`, plus every reason code that applied). They never touch the database, the clock or the network. The caller reads the facts (order status and age, amount already refunded, refunds in the window) under the row locks and hands them in. All thresholds live in `app/policy/rules.yaml` (auto-approve limit 500.00, 30-day order age, velocity of 3 refunds per 30 days, which statuses are refundable, which reasons exist and which are auto-approvable, admin-only and separation-of-duties actions). The loader rejects unknown keys, unknown statuses and floats, so a bad file stops the app from starting instead of silently weakening a rule. Precedence is `DENY` > `REQUIRE_APPROVAL` > `ALLOW`, and every outcome has a reason code that is written to `audit_logs`.

**Trade-off.** The caller must assemble the facts, so a handler could pass stale facts; that is why they are read inside the same transaction as the locks. Changing a rule means editing a reviewed file and redeploying, not toggling something at runtime. In exchange the engine is table-driven testable without a database (boundaries such as exactly 500.00, 500.01, a 30-day-old order, and the 3rd versus 4th refund are test rows), and eight mutations of it (off-by-one, limits hard-coded instead of read from the file, deny precedence, self-approval) are all caught.

## 12. One tool executor; the call is logged before it runs

**Context.** Golden rule 2 says every proposed action passes validate → authorize → policy → execute → log. A rule that every handler must remember to follow will eventually be forgotten.

**Decision.** `app/tools/executor.py` is the only way a tool runs. It first writes a `tool_calls` row and **commits it on its own**, so even a crash in the middle leaves a trace. Validation forbids unknown fields (so an argument can never carry a `user_id` or `role`), authorization checks the role from the authenticated `Actor`, and decide plus execute run in **one transaction** (the locks taken while deciding protect the writes that follow). A denied or failed call rolls that transaction back and records its outcome in a fresh one; a successful one records its audit row and its verdict in the same transaction as the effect. External side effects (the payout) run in an after-commit hook. The registry marks admin tools as not `agent_visible`, so the future model is never shown them. Stored `arguments` and `result` are capped (16 KiB, 32 KiB) with `CHECK` constraints as a backstop.

**Trade-off.** Two extra small transactions per call and a `tool_calls` table that grows with every attempt, denied ones included. The benefit is that a denied refund leaves a record in `tool_calls` and `audit_logs` but **nothing else** (no refund row, no event, no approval), which the tests and the demo check.

## 13. Refund idempotency: per-user key, request hash, and the provider's own key

**Context.** Retries, double-clicks and (later) repeated LLM proposals must never pay twice. Keys come from clients, so they cannot be trusted to be unique across users.

**Decision.** Three layers. (1) `UNIQUE(requested_by, idempotency_key)` in Postgres, written with `INSERT … ON CONFLICT DO NOTHING`; the key is required, 8–255 characters of a restricted set, and scoped **per user**, so two users may use the same key and get two refunds. (2) `request_hash`, a SHA-256 of the canonical payload (amounts are canonicalised as `Decimal`, so `250` and `250.00` hash the same); the same key with the same payload replays the stored refund (`200`, `Idempotent-Replayed: true`), the same key with a different payload is `409`. (3) The key sent to the payment provider is `refund-<refund uuid>`, **not** the user's key, so one user's key choice can never collide with another's at the provider. Redis is not involved.

**Trade-off.** Keys live as long as the refund row (there is no expiry), and a replay returns the refund's *current* state rather than a frozen copy. The strongest evidence is a test that fires ten identical requests at once and gets one refund row and one provider ledger entry; deliberately removing the `UNIQUE` constraint was caught by a test that had to be rewritten after the mutation run showed another lock was masking it (R1).

## 14. One lock order, and no external call inside a transaction

**Context.** Refund requests, approvals, rejections, payout finalisation and the reconcile job all touch the same order, customer and refund rows concurrently; the payment provider is slow and can fail.

**Decision.** `app/db/locking.py` defines the only lock order, **order → user → refund → approval**, with `FOR NO KEY UPDATE` locks (so foreign-key checks from unrelated inserts are not blocked). The order lock stops two refunds over-committing one order; the user lock serialises the per-customer velocity count. Approve and reject first read the approval and refund *without* locking only to learn the order id, then re-read everything under the locks. The payment provider is never called while a transaction or lock is open: a payout is three phases (read and commit; provider call; lock the refund and finalise), and the provider call is idempotent by `refund-<uuid>`.

**Trade-off.** More code than "do it all in one transaction", and a window between the commit and the finalisation in which a crash leaves the refund `processing`. `scripts/reconcile_refunds.py` closes that window by re-asking the provider with the same key (a repeat never pays twice), and it refuses the in-memory simulated provider unless `--allow-simulated`, because that provider's ledger does not survive a restart and a "re-ask" would pay again. A deterministic test overlaps a new request with an approve of the same order and checks that neither deadlocks.

## 15. A declined payout is a 201; an unknown outcome is a 202

**Context.** After the refund is accepted, the provider may say no, or may not answer at all. One HTTP status has to be chosen and documented.

**Decision.** The request was valid and the refund exists, so a **declined** payout is `201 Created` with `refund.status = "failed"` and an `error` object; it is not an HTTP error. A payout whose outcome is **unknown** (timeout, lost response) is `202 Accepted` with `refund.status = "processing"` and `error.code = "PAYOUT_UNCONFIRMED"`, to be settled by the reconcile job. A policy `DENY` is `403` and creates **no** refund row at all. A `failed` refund is terminal for its idempotency key: retrying with the same key replays the failure.

**Trade-off.** Clients must read `refund.status` and cannot rely on `2xx` meaning "money moved"; the contract is in [`refunds-api.md`](refunds-api.md). The alternative (an error status for a declined payout) would have made a retry with the same key ambiguous.

## 16. The approver must differ from the requester

**Context.** Anything above the automatic limit waits for a human. An admin who can file a refund and then approve it alone defeats the point of approval.

**Decision.** `approve_refund` is in `separation_of_duties_actions` in `rules.yaml`; the policy engine returns `DENY` with reason `SELF_APPROVAL` (HTTP `403`) when the deciding admin is the requester. `approve_refund` and `reject_refund` are also `admin_only_actions`, and `agent_visible = false`.

**Trade-off.** A team with one admin cannot approve their own requests. That is intentional; the rule is a line in a file, not a code change, if the business decides otherwise.

## 17. The outbox relay: ordered per aggregate, parked after repeated failure

**Context.** Consumers of refund events expect `requested` before `approved` before `completed`. A relay that retries a failed row while publishing the next one would reorder them.

**Decision.** `app/events/relay.py` selects due, unpublished, unparked rows with `FOR UPDATE … SKIP LOCKED` (so two relays never take the same row) and skips any row that has an earlier unpublished row for the same aggregate (ordered by the identity column `seq`, because `created_at` ties inside one transaction). The producer uses `acks=all` and idempotence, the Kafka key is the aggregate id (one refund's events stay in one partition, in order), and a row is marked published only **after** the broker acknowledges it. A failure increments `attempts` and delays the next try with exponential backoff (1 s doubling, capped at 300 s); after 10 attempts the row is **parked**. A parked row stops retrying but is still unpublished, so it deliberately **blocks later events for that aggregate** until `scripts/outbox_admin.py unpark` resets it.

**Trade-off.** One bad event can hold up a refund's later events, and an operator has to look at it. Skipping it silently would publish `completed` without `requested`. The relay's guarantees are checked by seven mutations (publish before produce, no `SKIP LOCKED`, no ordering check, no backoff, no parking, acks=1, un-park not resetting attempts).

## 18. Events carry ids and state only

**Context.** Events outlive requests: they are copied into topics, dead-letter topics and logs, where personal data is hard to remove.

**Decision.** The envelope (version 1) holds `event_id`, `event_type`, `occurred_at`, `request_id`, `aggregate_type`, `aggregate_id` and a `data` object limited to a per-event-type allow-list of ids, amounts, statuses and codes. No names, emails, subjects, notes or provider messages. The allow-list is enforced when the event is **written** (`add_event` raises) and again when it is **read** (a consumer dead-letters a message with extra fields or an unknown version). Anything richer is looked up by id.

**Trade-off.** A consumer that needs a customer's name must query for it. Adding a field is a deliberate schema change (a code edit, an update to [`events.md`](events.md), and a version decision), not something a handler can do by accident.

## 19. The consumer de-duplicates in the same transaction as its effect

**Context.** Delivery is at-least-once: a crash between "did the work" and "told the broker" means the message arrives again.

**Decision.** The notification consumer records `(consumer, event_id)` in `processed_events` (primary key) **in the same transaction as its effect**, then commits the Kafka offset **after** that transaction. A duplicate delivery hits the primary key and is skipped; a crash before the offset commit just redelivers. A malformed message, an unknown envelope version or a handler that keeps failing (5 attempts) is copied to `{prefix}.dead-letter` with the reason and then skipped, so one poison message cannot block the partition behind it. Today the "effect" is only a log line (`notification …`).

**Trade-off.** One more write per message, and the dead-letter topic needs someone to read it. The consumer's ordering of "effect, then offset" is guarded by mutations (offset first, no de-duplication check, poison message not skipped).

## 20. Mutation checks, hard deadlines and timeouts as part of testing

**Context.** A green test suite proves little if the tests would also be green with the code broken. Separately, a process or test that hangs is worse than one that fails.

**Decision.**

* **Mutation checks.** `scripts/mutation/run.py` introduces one deliberate defect at a time into the security- and correctness-critical code and requires the named tests to fail. There are **56 mutations in five lists** (policy engine 8, tool executor 10, refunds 14, outbox and consumer 14, dev-only scripts 10), and a normal test checks that every pattern still occurs exactly once, so the lists cannot rot. It has repeatedly found weak tests that were then fixed: the refund `UNIQUE` removal that a customer lock was masking (R1), a hang that left locks held and blocked the teardown (R2), a poison-message test that missed a trailing poison message and a restart (E10), a deadline mutation that was only "caught" by a 300 s hang (E13), and a cleanup test with a docstring that claimed a case it did not cover (C6).
* **Hard `--once` deadline.** `relay --once` and the consumer's `--once` exit with code **3** and a message naming what they were waiting on after `--deadline` seconds (default 120, `ONCE_DEADLINE_S`, `0` disables).
* **`kafka` marker.** Every test that uses the `kafka_env` fixture is marked automatically by a `conftest` hook, markers are strict, and a test fails if a Redpanda test is unmarked, so `-m "not kafka"` is a trustworthy Postgres-only suite (verified with the Redpanda container stopped).
* **`pytest-timeout`, 180 s per test.** On Windows its only method is *thread*: a hanging test ends the **whole** run with a stack dump (exit 1, no summary, later tests do not run) rather than failing alone. That is still the right trade (a visible stop instead of an endless wait) and a test pins the behaviour.
* **Real-process timeouts of 60 s** with a short application-level `--deadline`, because a cold Python start costs ~11 s of imports (the virtualenv's ~4,800 files are read cold). One fast-suite run once took 70 minutes for tests that normally take 2; it was not reproduced and is probably the machine sleeping.

**Trade-off.** A mutation run costs minutes and a sibling `ops_test` database nobody else may use meanwhile, so it is a deliberate step, not part of every test run. The timeouts add a dependency (`pytest-timeout`, approved) and a little ceremony to every real-process test.

## 21. Dev-only scripts for throw-away data refuse to run outside dev

**Context.** The Phase 2 demo needs to create customers, orders and refunds, and cleaning them up means deleting rows that the application otherwise treats as append-only history.

**Decision.** `scripts/demo_phase2.py` only ever **inserts** (a fresh `demo-…` customer and admin, delivered orders and succeeded payments per run, unique keys), so it is repeatable and never touches seeded data. `scripts/demo_cleanup.py` removes only the rows of users whose email starts with `demo-` and what belongs to them. It is a dry run unless `--apply` is given, runs in one transaction, prints exact counts, and stops without deleting anything if a demo row is entangled with real data. It **deliberately deletes `audit_logs` rows**, which are otherwise append-only, so both scripts check `APP_ENV` first through a helper that reads the raw value without building `Settings` (a non-dev environment would otherwise fail on settings validation before saying why) and exit `2` outside `dev` before touching anything.

**Trade-off.** The dev database accumulates demo rows until someone runs the cleanup, and the cleanup is the one place in the repository that removes audit rows. Keeping it a separate, dry-run-by-default, dev-only script (rather than an application feature) is what keeps that acceptable. Shipping it also meant testing it: 18 tests on `ops_test`, including the refusals, and 10 mutations.
