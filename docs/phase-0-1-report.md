## What was built

### Phase 0: Foundation

| Area | What exists |
|---|---|
| Infrastructure | `docker-compose.yml` with `pgvector/pgvector:pg16`, `redis:7-alpine` and Redpanda `v24.2.7` (single node, dev-container mode). Ports are published on `127.0.0.1` only |
| Config | `pydantic-settings` reading `.env` (`.env.example` provided) |
| Logging | structlog (console in dev, JSON when `APP_ENV=prod`); stdlib loggers routed through it |
| Request IDs | `RequestIDMiddleware` binds a `request_id` to every log line and echoes it as `X-Request-ID`. An inbound id is only accepted if it fully matches `[A-Za-z0-9_-]{8,64}`; otherwise a UUID is generated |
| Health | `GET /health` checks Postgres and Redis with a 2 s timeout each: `200` when both are fine, `503` with per-dependency `ok`/`error` otherwise |
| Repo hygiene | `.gitattributes` (`* text=auto eol=lf`), `.gitignore` |

Verified against real infrastructure: all three containers healthy; `/health` returned `200 {"status":"ok","postgres":"ok","redis":"ok"}`; with Redis stopped it returned `503 {"status":"degraded","postgres":"ok","redis":"error"}` and returned to `200` after Redis restarted, without restarting the API.

Phase 0 ended with 24 tests (`test_health` + `test_request_id`); Phase 1 added 106.

The database-backed tests use a separate `ops_test` database whose schema is built by running the real Alembic migration, with each test rolled back afterwards. The fixtures refuse to run against any database whose name does not end in `_test`.

What the security-relevant tests cover:

- **Login:** correct login; wrong password; unknown email (identical response to wrong password); inactive user; email normalisation; a password verification still runs for unknown emails; outdated hashes are upgraded; bad payloads give `422`.
- **Tokens:** expired; tampered payload; wrong secret; `alg=none`; wrong HMAC algorithm; missing `exp`; missing `sub`; non-UUID `sub`; token for a deleted user; token for an inactive user.
- **Authorisation:** a validly signed token that claims `role: admin` for a customer still gets customer powers; role changes take effect on the next request; `require_role` gives `403`; no token gives `401`.
- **Orders:** customer A cannot read customer B's order (`404`, and identical to a nonexistent order); A's list and `total` contain none of B's; admin reads any order; unauthenticated gets `401`; invalid UUID gives `422`; pagination limits are enforced and pages neither overlap nor miss rows.
- **Schema:** refund `idempotency_key` uniqueness and `NOT NULL`; money `CHECK`s; unknown status rejected; `RESTRICT` on deleting a paid order; exact `Decimal` round trip; pgvector installed; models match migrations (`alembic check`).

## Mutation testing

Passing tests prove little unless they fail when the code is wrong. For the security-critical paths, one defect at a time was introduced into the source, the relevant tests were run, and the source was restored (the working tree was verified clean afterwards). A mutation is **caught** when at least one test fails.

Results (run on 2026-10-07; restored tree: 130 passed):

| ID | Defect introduced | Result |
|---|---|---|
| M1 | Request-ID check uses `^…$` with `match` instead of `fullmatch` | **Caught** (1 failed: the trailing-newline case) |
| A1 | JWT signature verification disabled | **Caught** (9 failed) |
| A2 | `"none"` added to the allowed JWT algorithms | **Survived — equivalent mutation** (see below) |
| A3 | `exp` no longer required | **Caught** (2 failed) |
| A4 | `get_current_user` ignores `is_active` | **Caught** (1 failed) |
| A5 | Login skips the dummy verify for unknown emails | **Caught** (1 failed) |
| A6 | Login ignores `is_active` | **Caught** (1 failed) |
| A7 | Login never rehashes outdated hashes | **Caught** (1 failed) |
| A8 | `require_role` allows everyone | **Caught** (3 failed) |
| O1 | `get_order` drops the owner filter | **Caught** (5 failed) |
| O2 | `list_orders` drops the owner filter | **Caught** (9 failed) |
| O3 | Orders service treats every role as unscoped | **Caught** (13 failed) |
| O4 | Router returns `403` instead of `404` | **Caught** (6 failed) |
| O5 | List `total` count not scoped to the owner | **Caught** (4 failed) |

**13 of 14 caught.** A2 survives because PyJWT itself refuses to verify an `alg=none` token whenever a key is supplied, so adding `"none"` to the allow-list changes nothing observable. The `alg=none` token is therefore rejected twice (by the pinned allow-list and by PyJWT), and the tests that send such a token pass either way. It is a defence-in-depth finding, not a test gap.

Limits of this approach: the mutations were chosen by hand, run by a throwaway shell script (copy file, `sed` one change, run tests, restore) that is **not committed to the repo**, and cover the auth and orders paths, not the whole code base. No mutation-testing tool such as `mutmut` is configured.

## Open items going into Phase 2

Requested items first.

1. **Refund idempotency should be per-user and bound to the request.** Today `refunds.idempotency_key` is globally `UNIQUE`. Replace it with `UNIQUE (requested_by, idempotency_key)` and store a hash of the request body (`request_hash`). The same key with the same hash returns the original result; the same key with a *different* hash is rejected (`409`/`422`). Without this, one user's key can collide with another's, and reusing a key with a different amount is not detected. Needs migration `0002` (hand-review the CHECKs).
2. **Review the status enums before real data exists.** `refund_status`, `approval_status`, `tool_call_status`, `workflow_status`, `payment_status`, `order_status` and the ticket enums are first drafts written before the Phase 2 state machines. For example, there is no refunded / partially-refunded state on `orders` or `payments`. Changing one means dropping and re-adding its `CHECK`.
3. **Login rate limiting.** There is none today, so brute-force protection is absent. Add Redis-backed limits per IP and per account, with backoff.
4. **Redpanda advertised listener is `localhost:9092`; switch to `127.0.0.1` and test with a real producer when the outbox relay is built (Phase 2).** Nothing has connected to Redpanda yet, so the listener configuration (and its healthcheck) is **unverified** beyond `rpk cluster info` inside the container.

Also noticed:

- **No token revocation or refresh**; tokens live 30 minutes. Deactivation and deletion are immediate only because the user is reloaded per request.
- **Timing equalisation is tested structurally** (a verification runs for unknown emails); response times were never measured.
- **`alembic check` does not compare `CHECK` constraints** (per Alembic's documentation; not re-tested), so a mismatch between a model enum and the database constraint would go unnoticed. Consider a test comparing enum values to the constraint definitions.
- **`audit_logs` is meant to be append-only but nothing enforces it** (no trigger or revoked privileges).
- **`outbox_events` and `workflow_runs` are schema only**; no code writes them yet.
- **The mutation script is not in the repo**, and there is no CI.
- **Unverified:** the Mac/Linux commands in the README (`.venv/bin/...`, `python3`) were not run, since this was developed on Windows; the Mermaid diagrams were syntax-checked but not viewed rendered.
